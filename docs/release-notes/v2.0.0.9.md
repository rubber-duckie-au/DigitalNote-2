# DigitalNote XDN v2.0.0.9

Consensus-hardening release. This build takes the masternode voted-payee
consensus introduced in v2.0.0.8 and makes it **safe to activate on
mainnet**: it wires the previously-stranded mainnet activation height,
adds a deterministic devops rescue path so the chain can never dead-stall
below the consensus floor, closes a proof-of-work readiness gap that
caused a real testnet stall, and rebuilds the encrypted messenger around a
modern chat UI.

**Chain-compatible with v2.0.0.8 — no consensus rule changes.** The network
protocol is bumped to 62059, but older clients still connect, sync, and
validate identically. Every block v2.0.0.9 accepts, v2.0.0.8 accepts, and
vice versa. Voted consensus remains gated behind the activation height and
the network spork key. **No mandatory upgrade, no fork.**

---

## 🛟 Consensus Resilience — devops rescue *(headline feature)*

v2.0.0.8 could, in principle, dead-stall: post-activation, if the fleet
falls below the consensus floor (fewer than 5 voting-eligible masternodes)
or the vote queues fail to form, no payee resolves and no valid block can
be produced. v2.0.0.9 adds an escape hatch — one that stays entirely on
the production side of the consensus boundary.

- **The rule (one sentence):** post-activation, when no voted payee can be
  resolved and `block.nTime - parent.GetMedianTimePast() >= 30 minutes`, a
  producer mints a block paying the **devops** address in the masternode
  slot, which re-seeds vote production and lets normal consensus resume.
- **The rescue is a production policy, not a consensus rule.** This is the
  most important property of the design and the one to read twice.
  `ShouldMintRescueBlock()` is called **only from block-production paths**
  — the staker, the miner, and the mining RPCs. It is **never** called from
  `CheckBlock()`. Validation behaviour is byte-for-byte identical to
  v2.0.0.8: a devops masternode-slot payee is accepted post-activation on
  exactly the same terms as before. Two nodes may legitimately disagree
  about whether to *mint* a rescue block and both remain correct, because
  neither *rejects* the other's block. **No fork, no activation ceremony,
  no coordinated upgrade.**
- **Why a devops payee rather than a real masternode:** a real-masternode
  fallback is only safe if the whole fleet agrees which masternode — and
  when views diverge, that disagreement *is* the stall. The devops address
  is height-derived from the existing ladder and already valid under
  v2.0.0.8 rules, so a rescue block is verifiable from chain data alone.
  Voted consensus still pays real masternodes whenever it forms (the common
  case); devops is the floor, not the norm.
- **Evidence gate — a node cannot mistake its own ignorance for a network
  deadlock.** Before an empty vote tracker counts as evidence that no payee
  exists, the node must have been *capable of learning* one: at least
  **3 connected peers**, out of initial block download, for at least
  **1 hour** (`RESCUE_MIN_PEERS`, `RESCUE_MIN_OBSERVATION_SECS`). A node
  that has just restarted inherits an empty tracker by definition and a
  chain-relative stall instantly; without this gate it would rescue within
  seconds of starting. These are **policy constants, not consensus
  constants** — changing them cannot split the chain.
- **No new activation constant:** the rescue reuses the existing
  `GetEffectiveVotedConsensusActivationHeight()` and rides the same
  activation boundary — nothing new to coordinate.

## 🗳️ Mainnet Voted-Consensus Activation *(now actually reachable)*

- **Fixed the stranded mainnet activation height.** In v2.0.0.8 the mainnet
  activation resolved to `INT_MAX` — voted consensus could *never* activate
  on mainnet no matter how long the chain ran. v2.0.0.9 wires the real
  floor: **mainnet block 1,480,000** (testnet 2000, unchanged).
- `SPORK_15` can still bring activation **forward**, never push it back.
- **Protocol version bumped to 62059** so consensus-capable builds are
  visible in the version handshake ahead of the activation decision. The
  voting-eligibility floor (`MIN_VOTING_PROTOCOL_VERSION`) is deliberately
  held at 62058 so the entire v2.0.0.8 masternode fleet continues to count
  toward consensus the moment v2.0.0.9 ships — a lockstep bump there would
  have emptied the consensus denominator and induced the very dead-stall
  the rescue above exists to prevent.

## ⛏️ Proof-of-Work Readiness Gate

- **Fixed a missing consensus-readiness gate on every PoW block-production
  path** (`getworkex`, `getwork`, `getblocktemplate`, and the `mintblock`
  debug RPC). The PoS staking path already refused to build blocks before
  voted consensus was ready; the PoW paths did not, which **caused an
  actual testnet chain stall**. All PoW entry points now enforce the same
  readiness check as PoS.

## 🔐 Proof-of-Stake Bring-up

- **Fixed a startup crash when enabling staking on a proof-of-work-only
  chain.** On a fresh chain with no PoS blocks yet, the last-stake-block
  lookup walked back to the genesis block and dereferenced its (null)
  parent. Guarded with a proper genesis/parent null check, so a brand-new
  chain can transition into PoS cleanly.

## 💬 Encrypted Messenger — Redesigned

The SMSG messenger has been rebuilt from the ground up around a modern
two-pane chat interface, replacing the dated single-pane page and the
2013-era rich-text plugin.

- **Two-pane layout:** conversation list on the left, live thread on the
  right, with chat bubbles (sent right, received left) rendered via
  `QTextDocument` for inline images and basic rich text.
- **New chat composer** replacing the abandoned MRichTextEdit plugin:
  bold / italic / underline / strikethrough / link / colour, Enter-to-send
  (Shift+Enter for a newline), emoji picker.
- **Emoji support:** 261 standard emoji plus 4 XDN custom emoji, addressable
  by shortcode (e.g. `:xdn:`) and rendered inline as images both while
  composing and in the message thread.
- Conversation previews are HTML-stripped and show a muted single-line
  summary with the counterparty and the receiving address.
- **Fixed: sent messages missing from the Sent list on some wallets.** The
  sender's own outbox copy was encrypted to "the first owned address in the
  address book" rather than the address the user actually sent from. That
  entry varies per wallet, was only format-checked and never checked for a
  retrievable key, and if it happened to be a stealth, watch-only, or
  otherwise keyless address the outbox copy was either not written or
  written under a key the wallet could not decrypt. The recipient's copy was
  unaffected — so the message genuinely sent, but never appeared in the
  sender's own Messages tab, and only on some wallets, which made it look
  random. The outbox copy is now encrypted to the user-selected sending
  address, which is guaranteed owned and already proven encryptable. An
  anonymous send with no usable from-address still falls back to the first
  owned, usable address.
- Fixed several redesign-era issues: messages bouncing back to the list
  instead of staying in the open thread on send, emoji aspect-ratio and
  icon rendering, and vertical layout sizing.

## 🛡️ Wallet & Maintenance Hardening

- **Recovery routing.** The auto-verify-and-recover path on wallet load no
  longer bypasses the `-salvagewallet` deprecation gate; recovery is routed
  through the safe rebuild path (`RebuildWallet`) rather than the deprecated
  BDB salvage.
- **Berkeley DB error reporting.** Database error paths now name the file
  and translate the error code instead of surfacing an empty filename.

## 📡 Peer Reliability

- **`dseep` relay de-duplication.** Repeated `dseep` announcements are now
  de-duplicated before relay, eliminating a bandwidth- and log-flood
  amplification path observed under sustained fleet operation.
- **Velocity difficulty recovery.** The VRX difficulty-recovery curve now
  measures stall time as `max(block spacing, elapsed since the previous
  block)`, so the recovery loop engages reliably on a genuinely stalled
  chain instead of depending on the phase of the tip timestamp. Previously
  the curve could fail to engage — leaving a stalled chain with no
  automatic difficulty relief — and produced spurious difficulty errors in
  the log while doing so. Both are resolved.
- **Masternode list recovery on a stalled chain.** `dsee` / `dseep`
  processing was gated behind a synchronisation check that reports false
  whenever the chain tip is more than an hour old. A node on a stalled
  chain therefore refused the very messages that would repopulate its
  masternode list, and could never recover a quorum on its own — a stall
  made its own recovery impossible. List population is now governed by a
  dedicated check with no stale-tip test. Field-validated: a node with a
  27-hour-old tip repopulated from 0 to 8 masternodes and met the
  consensus floor.

## 🔧 New Diagnostics

- **`getdeploymentstatus` RPC** *(new)* — read-only deployment and
  activation-readiness telemetry, with no new consensus state. Reports the
  build's protocol version and whether it is consensus-capable; the
  effective activation height, spork-15 override state, and blocks
  remaining; the share of connected peers running a consensus-capable
  build; and — the safety signal — the number of voting-eligible
  masternodes versus the consensus floor. Intended to answer the
  "is the network ready to activate?" question from a single call.
- The `checkblock` debug category now surfaces both consensus outcomes per
  validated block (voted-payee match, and consensus fallback with height),
  so operators can measure the post-activation fallback rate directly from
  the log with `-debug=checkblock`.

## 🖥️ Version & Housekeeping

- Client version reports **2.0.0.9**; internal version strings standardised
  to the four-part `2.0.0.9` form across the source.
- The rescue predicate was renamed `IsRescueActive()` → `ShouldMintRescueBlock()`
  so the name states what it is: a producer-side decision, not a validity
  test. Guardrail comments at both former validator call sites record that
  it must never be reintroduced into `CheckBlock()`. Because the rescue no
  longer sits in consensus, the parallel Rust implementation **does not need
  to mirror the predicate at all** — a producer-side heuristic requires no
  cross-implementation agreement.
- Version regression tests rewritten to the current constants, including a
  guard that fails the build if the voting-eligibility floor is ever raised
  in lockstep with the protocol version.

## 📦 Dependency Uplift

The final dependency modernisation before the planned v3 line.

- **OpenSSL upgraded 1.1.1w → 3.5.7.** OpenSSL 1.1.1 has been end-of-life
  since September 2023; the wallet now builds against the current 3.5.x LTS
  branch. The raw EC / BN / ECDSA / RIPEMD calls used by SMSG, stealth
  addressing, and the bignum layer are marked deprecated in OpenSSL 3.x but
  remain fully available; deprecation diagnostics are suppressed so they do
  not break `-Werror` builds. Migrating those call sites to the modern
  EVP / OSSL_PARAM 3.x API is tracked as future work.
- **Boost upgraded to 1.91.0.**
- **Web-wallet connector migrated from websocketpp to Boost.Beast.** The
  vendored websocketpp 0.8.2 library depended on `boost::asio::io_service`,
  which was removed in Boost 1.87 — so the Boost uplift required replacing
  it. The connector was rewritten on Boost.Beast with its wire behaviour
  preserved 1:1: the same JSON frames, the same text-opcode framing, and
  the same broadcast semantics, so connected web-wallet clients see no
  difference.
- **Boost.Asio API migrations.** Beyond the connector rewrite, the uplift
  removed several APIs the RPC and SSL layers relied on:
  `boost::asio::deadline_timer` (dropped from `boost/asio.hpp` in 1.89),
  `address_v6::is_v4_compatible()` / `to_v4()`, and the old
  `resolver::query` / `resolver::iterator` forms. All call sites were
  migrated to the supported equivalents with behaviour unchanged.

## ⚙️ Build & Release

- **macOS deployment target pinned consistently.** All prerequisite
  libraries and the wallet link now target macOS 12 (Monterey) explicitly,
  independent of the CI runner's SDK. Previously the prerequisite libraries
  inherited the runner's default SDK, which broke the link when GitHub's

- CI continues to build the full six-target matrix: Windows x64, Linux x64,

## 📅 Coming up: devops address rotation at block 1,280,000

**This release does not change the devops address.** This notice is advance warning
of a scheduled change that has been in the code since v2.0.1.0 groundwork landed, so
operators have time to prepare.

### What happens

At **mainnet block 1,280,000**, the address receiving the devops portion of each block
reward changes:

| | Address |
| --- | --- |
| Blocks up to and including **1,279,999** | `dafC1LknpDu7eALTf5DPcnPq2dwq7f9YPE` |
| Blocks from **1,280,000** onward | `dGoFPie9QZmQ1Ty1beqSHytxNruehpGtGa` |

The boundary is **inclusive** — block 1,280,000 itself pays the new address. There is no
transition window and no grace period.

At that same height, validation of the devops payee changes from log-only to **strict**:
from block 1,280,000 onward, a block paying the old address is **rejected by the network**.

### Who needs to do something

**Almost nobody.** If your software obtains block templates via `getblocktemplate`, the
correct address is supplied per template and resolved from the target height — this is
handled automatically and no action is required. Standard wallets, stakers, and
masternode operators running v2.0.0.8 or later need do nothing.

**The exception that matters:** any mining pool, staking service, or custom block-building
software with the devops address **hardcoded**. From block 1,280,000 those blocks will be
rejected and the work lost. If you maintain such software, check now:

```
grep -r "dafC1LknpDu7eALTf5DPcnPq2dwq7f9YPE" .
```

Any hit outside historical data or documentation needs updating, or switching to
`getblocktemplate`.

**Masternode payments are unaffected.** Only the devops payee changes.

### This is not a fork

No consensus rules change at the rotation. It is a scheduled change to a payment
destination that every v2.0.0.8-and-later node already computes from the block height.
There is no coordinated upgrade, no activation ceremony, and no mandatory update beyond
being on v2.0.0.8 or later.

The mechanism was exercised successfully on testnet during the v2.0.0.8 cycle at the
testnet rotation boundary, and the code path that resolves and enforces the address is
unchanged since that release.

### Full operator playbook

A complete playbook — pre-rotation checklist, day-of checklist, how to confirm it worked,
and what to do if something goes wrong — is in the repository at:

```
docs/operator/v2.0.1.0-rotation-playbook.md
```

Exchanges and pool operators in particular should read it. The short version: if you use
`getblocktemplate`, confirm and carry on; if you have a hardcoded address, update it before
the chain reaches 1,280,000.

### Estimating the date

The trigger is a **block height, not a date**. At the target 120-second spacing 1,280,000
is roughly 3.5 months out from block 1,204,783; at the observed longer-term rate it is
closer to 5.5 months. Any specific date in circulation is an estimate and will drift —
track the height.

## ⚠️ Upgrade Notes

- **Chain-compatible with v2.0.0.8.** Network protocol bumped to 62059;
  older clients still connect and sync.
- The v2.0.0.8 masternode fleet (protocol 62058) continues to count toward
  voted consensus — no masternode is dropped from consensus eligibility by
  upgrading.
- Voted consensus remains inactive on mainnet until block **1,480,000** (or
  earlier if brought forward by `SPORK_15`).
- No mandatory upgrade.

**Recommended upgrade order for masternode operators:**
1. Masternodes
2. Mining pools
3. Stakers
4. Full nodes

## 🔍 MISC

- No new consensus constants were introduced by the rescue mechanism; it is
  derived entirely from the existing activation height and committed block
  timestamps.
- The devops rescue payee is taken from the existing height-indexed devops
  address ladder, so a rescue block is identifiable and verifiable from
  chain data alone.
