# DigitalNote XDN v2.0.0.9

Consensus-hardening release. This build takes the masternode voted-payee
consensus introduced in v2.0.0.8 and makes it **safe to activate on
mainnet**: it wires the previously-stranded mainnet activation height,
adds a deterministic devops rescue path so the chain can never dead-stall
below the consensus floor, closes a proof-of-work readiness gap that
caused a real testnet stall, and rebuilds the encrypted messenger around a
modern chat UI.

**Chain-compatible with v2.0.0.8.** The network protocol is bumped to
62059, but older clients still connect and sync. Voted consensus remains
gated behind the activation height and the network spork key. No mandatory
upgrade.

---

## 🛟 Consensus Resilience — devops rescue *(headline feature)*

v2.0.0.8 could, in principle, dead-stall: post-activation, if the fleet
falls below the consensus floor (fewer than 5 voting-eligible masternodes)
or the vote queues fail to form, no payee resolves and no valid block can
be produced. v2.0.0.9 adds a deterministic escape hatch.

- **The rule (one sentence):** post-activation, when
  `block.nTime - parent.GetMedianTimePast() >= 30 minutes`, producers mint
  — and validators accept — a block paying the **devops** address in the
  masternode slot.
- **Deterministic, not "fair":** a real-masternode fallback is only fair if
  the whole fleet agrees which masternode — and when views diverge, that
  disagreement is precisely the stall. The devops address is
  height-derived, identical on every node, and already valid under
  `CheckBlock`, so every node computes the same rescue block. Voted
  consensus still pays real masternodes whenever it forms (the common
  case); devops is the floor, not the norm.
- **No new activation constant:** the rescue reuses the existing
  `GetEffectiveVotedConsensusActivationHeight()` and rides the same
  activation boundary — nothing new to coordinate.
- **Tightened validation:** post-activation, a devops masternode-slot payee
  is now accepted **only** when the 30-minute stall condition holds, rather
  than unconditionally. Stricter than before, same activation boundary.

## 🗳️ Mainnet Voted-Consensus Activation *(now actually reachable)*

- **Fixed the stranded mainnet activation height.** In v2.0.0.8 the mainnet
  activation resolved to `INT_MAX` — voted consensus could *never* activate
  on mainnet no matter how long the chain ran. v2.0.0.9 wires the real
  floor: **mainnet block 1,480,000** (testnet 2000, unchanged).
- `SPORK_15` can still bring activation **forward**, never push it back.
- **Protocol version bumped to 62059** so consensus-capable builds are
  visible in the version handshake ahead of the activation decision. The
  voting-eligibility floor (`MIN_VOTING_PROTOCOL_VERSION`) is deliberately
  held at 62058 so the entire v2.0.0.8 masternode fleet continues to count
  toward consensus the moment v2.0.0.9 ships — a lockstep bump there would
  have emptied the consensus denominator and induced the very dead-stall
  the rescue above exists to prevent.

## ⛏️ Proof-of-Work Readiness Gate

- **Fixed a missing consensus-readiness gate on every PoW block-production
  path** (`getworkex`, `getwork`, `getblocktemplate`, and the `mintblock`
  debug RPC). The PoS staking path already refused to build blocks before
  voted consensus was ready; the PoW paths did not, which **caused an
  actual testnet chain stall**. All PoW entry points now enforce the same
  readiness check as PoS.

## 🔐 Proof-of-Stake Bring-up

- **Fixed a startup crash when enabling staking on a proof-of-work-only
  chain.** On a fresh chain with no PoS blocks yet, the last-stake-block
  lookup walked back to the genesis block and dereferenced its (null)
  parent. Guarded with a proper genesis/parent null check, so a brand-new
  chain can transition into PoS cleanly.

## 💬 Encrypted Messenger — Redesigned

The SMSG messenger has been rebuilt from the ground up around a modern
two-pane chat interface, replacing the dated single-pane page and the
2013-era rich-text plugin.

- **Two-pane layout:** conversation list on the left, live thread on the
  right, with chat bubbles (sent right, received left) rendered via
  `QTextDocument` for inline images and basic rich text.
- **New chat composer** replacing the abandoned MRichTextEdit plugin:
  bold / italic / underline / strikethrough / link / colour, Enter-to-send
  (Shift+Enter for a newline), emoji picker.
- **Emoji support:** 261 standard emoji plus 4 XDN custom emoji, addressable
  by shortcode (e.g. `:xdn:`) and rendered inline as images both while
  composing and in the message thread.
- Conversation previews are HTML-stripped and show a muted single-line
  summary with the counterparty and the receiving address.
- Fixed several redesign-era issues: messages bouncing back to the list
  instead of staying in the open thread on send, emoji aspect-ratio and
  icon rendering, and vertical layout sizing.

## 🛡️ Wallet & Maintenance Hardening

- **Recovery routing.** The auto-verify-and-recover path on wallet load no
  longer bypasses the `-salvagewallet` deprecation gate; recovery is routed
  through the safe rebuild path (`RebuildWallet`) rather than the deprecated
  BDB salvage.
- **Berkeley DB error reporting.** Database error paths now name the file
  and translate the error code instead of surfacing an empty filename.

## 📡 Peer Reliability

- **`dseep` relay de-duplication.** Repeated `dseep` announcements are now
  de-duplicated before relay, eliminating a bandwidth- and log-flood
  amplification path observed under sustained fleet operation.
- **Velocity wall-clock guard.** The Velocity difficulty check no longer
  produces spurious rejections on the bootstrap / clock-skew path when a
  node resumes after being idle.

## 🔧 New Diagnostics

- **`getdeploymentstatus` RPC** *(new)* — read-only deployment and
  activation-readiness telemetry, with no new consensus state. Reports the
  build's protocol version and whether it is consensus-capable; the
  effective activation height, spork-15 override state, and blocks
  remaining; the share of connected peers running a consensus-capable
  build; and — the safety signal — the number of voting-eligible
  masternodes versus the consensus floor. Intended to answer the
  "is the network ready to activate?" question from a single call.
- The `checkblock` debug category now surfaces both consensus outcomes per
  validated block (voted-payee match, and consensus fallback with height),
  so operators can measure the post-activation fallback rate directly from
  the log with `-debug=checkblock`.

## 🖥️ Version & Housekeeping

- Client version reports **2.0.0.9**; internal version strings standardised
  to the four-part `2.0.0.9` form across the source.
- Corrected an inaccurate code comment describing the rescue predicate as a
  pure function of committed chain data (it depends in part on node-local
  vote-queue state); documented the real determinism boundary for the
  benefit of the parallel Rust reimplementation. No behavioural change.
- Version regression tests rewritten to the current constants, including a
  guard that fails the build if the voting-eligibility floor is ever raised
  in lockstep with the protocol version.

## 📦 Dependency Uplift

The final dependency modernisation before the planned v3 line.

- **OpenSSL upgraded 1.1.1w → 3.5.7.** OpenSSL 1.1.1 has been end-of-life
  since September 2023; the wallet now builds against the current 3.5.x LTS
  branch. The raw EC / BN / ECDSA / RIPEMD calls used by SMSG, stealth
  addressing, and the bignum layer are marked deprecated in OpenSSL 3.x but
  remain fully available; deprecation diagnostics are suppressed so they do
  not break `-Werror` builds. Migrating those call sites to the modern
  EVP / OSSL_PARAM 3.x API is tracked as future work.
- **Boost upgraded to 1.91.0.**
- **Web-wallet connector migrated from websocketpp to Boost.Beast.** The
  vendored websocketpp 0.8.2 library depended on `boost::asio::io_service`,
  which was removed in Boost 1.87 — so the Boost uplift required replacing
  it. The connector was rewritten on Boost.Beast with its wire behaviour
  preserved 1:1: the same JSON frames, the same text-opcode framing, and
  the same broadcast semantics, so connected web-wallet clients see no
  difference.

## ⚙️ Build & Release

- **macOS deployment target pinned consistently.** All prerequisite
  libraries and the wallet link now target macOS 12 (Monterey) explicitly,
  independent of the CI runner's SDK. Previously the prerequisite libraries
  inherited the runner's default SDK, which broke the link when GitHub's
  runner image advanced.
- CI continues to build the full six-target matrix: Windows x64, Linux x64,
  Linux x64 (compat), Linux aarch64, macOS Intel, and macOS Apple Silicon.

## ⚠️ Upgrade Notes

- **Chain-compatible with v2.0.0.8.** Network protocol bumped to 62059;
  older clients still connect and sync.
- The v2.0.0.8 masternode fleet (protocol 62058) continues to count toward
  voted consensus — no masternode is dropped from consensus eligibility by
  upgrading.
- Voted consensus remains inactive on mainnet until block **1,480,000** (or
  earlier if brought forward by `SPORK_15`).
- No mandatory upgrade.

**Recommended upgrade order for masternode operators:**
1. Masternodes
2. Mining pools
3. Stakers
4. Full nodes

## 🔍 MISC

- No new consensus constants were introduced by the rescue mechanism; it is
  derived entirely from the existing activation height and committed block
  timestamps.
- The devops rescue payee is taken from the existing height-indexed devops
  address ladder, so a rescue block is identifiable and verifiable from
  chain data alone.
