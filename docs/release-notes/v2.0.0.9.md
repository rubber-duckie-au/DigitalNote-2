# DigitalNote XDN v2.0.0.9

Consensus-hardening release. This build hardens the masternode voted-payee
consensus introduced in v2.0.0.8 in preparation for a future mainnet
activation: it adds a devops rescue path (a producer-side escape hatch) so
that, once voted consensus is active, the chain cannot dead-stall below the
consensus floor, closes a proof-of-work readiness gap that caused a real
testnet stall, and rebuilds the encrypted messenger around a modern chat UI.

**Voted consensus is NOT scheduled on mainnet in this release.** The mainnet
activation height is unset (`INT_MAX`), and mainnet ignores `SPORK_15`, so on
mainnet every v2.0.0.9 node stays on the pre-activation payment path: each
block producer picks the masternode payee from its own list, exactly as under
v2.0.0.8. Testnet keeps its activation at block 2000. A later release will
schedule mainnet activation (see *Mainnet Voted-Consensus Activation*).

**Chain-compatible with v2.0.0.8.** The network protocol is bumped to 62059,
but older clients still connect, sync and follow the same chain. One
qualifier: v2.0.0.9 allows a block timestamp up to three minutes ahead of its
own clock (v2.0.0.8: 45 seconds), so a block stamped 45 to 180 seconds ahead
is taken by v2.0.0.9 but declined, at that moment, by a v2.0.0.8 node (see
*Peer Reliability*). That affects when a block is first accepted, not which
chain is valid. **No mandatory upgrade and no fork** — but note the separate
devops address rotation at block 1,280,000, which requires v2.0.0.8 or later
(see *Coming up*, below).

---

## 🛟 Consensus Resilience — devops rescue *(headline feature)*

- **The rescue now measures a stall the way you would.** It waited for the chain
  to be stalled for 30 minutes, but measured that against a rolling median of the
  last eleven block times rather than the most recent block. The median lags the
  chain by roughly a quarter of an hour, so the rescue was firing after about
  fifteen minutes — and, once triggered, kept firing while blocks were arriving
  less than a minute apart. It now measures from the previous block, so thirty
  minutes means thirty minutes.
- **A wallet that cannot see the whole masternode list no longer mints rescue
  blocks on its own.** A node whose list was incomplete could conclude the network
  had too few masternodes, and pay the development fund instead of a masternode —
  while the network was perfectly healthy and every other node accepted the
  result. Such a node now waits ten minutes, asks its peers for the full list, and
  only then proceeds. **It always proceeds eventually**: if the missing
  masternodes are genuinely gone, the chain must still be able to recover.
- **That same check no longer mistakes a healthy wallet for a blind one.** A
  wallet rebuilds its masternode list from a cache when it restarts, and the
  check was not told about the entries restored that way — so after every
  restart a wallet with a complete list believed it was missing everybody, and
  would have delayed every rescue by ten minutes indefinitely. It now counts the
  restored entries.
- **A rescue block is no longer mistaken for a missing masternode.** Rescue
  blocks pay the development fund in the masternode slot, and the check read
  those payments as evidence of a masternode it had never heard of. One rescue
  was enough to make a wallet consider itself blind for the next two hundred
  blocks — delaying the very rescues it was meant to protect.
- **The network now recovers from a full restart without needing a rescue
  block at all.** Masternodes publish their payment ordering when a block
  arrives, which left a gap: if every wallet on the network restarted while the
  chain was between blocks, nobody published, so no payee could be agreed, so no
  block could be produced — and the only way out was to wait half an hour for a
  rescue block and pay the development fund instead of a masternode. A
  masternode now notices when the chain has been still for several minutes with
  no contribution of its own on record, and publishes once, unprompted. In
  testing this turned a 101-minute stall that ended in a diverted payment into a
  normal block three and a half minutes later, with nothing diverted.

The rescue only applies once voted consensus is active, so in v2.0.0.9 it is
live on **testnet only** (mainnet activation is not scheduled).

v2.0.0.8 could, in principle, dead-stall: post-activation, if the fleet
falls below the consensus floor (fewer than 5 voting-eligible masternodes)
or the vote queues fail to form, no payee resolves and no valid block can
be produced. v2.0.0.9 adds an escape hatch — one that stays entirely on
the production side of the consensus boundary.

- **The rule (one sentence):** post-activation, when no voted payee can be
  resolved and about 30 minutes have passed since the previous block, by the
  producer's own clock, a producer mints a block paying the **devops**
  address in the masternode slot, which re-seeds vote production and lets
  normal consensus resume. (Proof-of-stake timestamps are rounded down to
  16-second steps, so the gap recorded in the chain between a rescue block
  and its parent can be slightly under 30 minutes, e.g. 1,785 seconds.)
- **The rescue is a production policy, not a consensus rule.** This is the
  most important property of the design and the one to read twice.
  `ShouldMintRescueBlock()` is called **only from block-production paths**
  — the staker, the miner, and the mining RPCs. It is **never** called from
  `CheckBlock()`. Validation behaviour is byte-for-byte identical to
  v2.0.0.8: a devops masternode-slot payee is accepted post-activation on
  exactly the same terms as before. Two nodes may legitimately disagree
  about whether to *mint* a rescue block and both remain correct, because
  neither *rejects* the other's block. **No fork, no activation ceremony,
  no coordinated upgrade.**
- **Why a devops payee rather than a real masternode:** a real-masternode
  fallback is only safe if the whole fleet agrees which masternode — and
  when views diverge, that disagreement *is* the stall. The devops address
  is height-derived from the existing ladder and already valid under
  v2.0.0.8 rules, so every node accepts a rescue block. The *decision* to
  mint one is not deterministic: it depends on each producer's own view
  (its clock, peers, vote queues and masternode list), and producers may
  differ on when to use it. Voted consensus still pays real masternodes
  whenever it forms (the common case); devops is the floor, not the norm.
- **Evidence gate — a node cannot mistake its own ignorance for a network
  deadlock.** Before an empty vote tracker counts as evidence that no payee
  exists, the node must have been *capable of learning* one: at least
  **3 connected peers**, out of initial block download, for at least
  **1 hour** (`RESCUE_MIN_PEERS`, `RESCUE_MIN_OBSERVATION_SECS`). A node
  that has just restarted inherits an empty tracker by definition and a
  chain-relative stall instantly; without this gate it would rescue within
  seconds of starting. These are **policy constants, not consensus
  constants** — changing them cannot split the chain.
- **No new activation constant:** the rescue reuses the existing
  `GetEffectiveVotedConsensusActivationHeight()` and rides the same
  activation boundary — nothing new to coordinate.

## 🗳️ Mainnet Voted-Consensus Activation *(not scheduled in this release)*

- **Mainnet activation is NOT scheduled in v2.0.0.9.** Earlier v2.0.0.9
  release candidates wired a mainnet activation height of 1,480,000. From
  rc9 that is withdrawn: the mainnet activation height is `INT_MAX` again
  (as in v2.0.0.8), so voted consensus does not activate on mainnet with
  this release. A later release will schedule it. Testnet keeps block 2000.
- **Mainnet ignores `SPORK_15`.** On mainnet the spork cannot activate voted
  consensus. On testnet a `SPORK_15` value below 2000 lowers the activation
  height; any other value is ignored. Sporks are not one-way: a newer spork
  message replaces the old value, and spork values are not stored across a
  restart, so on testnet the effective height can move.
- **Protocol version bumped to 62059** so v2.0.0.9 builds are visible in
  the version handshake ahead of a future activation decision.
- **Which masternodes count toward the voting threshold no longer depends on
  their advertised version.** The count is now decided by committed chain data
  alone: a masternode counts once its collateral is deep enough. Previously a
  masternode advertising a protocol version below 62058 was left out — but that
  version is stamped by whichever wallet last started the masternode, and two
  nodes can hold different values for the same masternode, so they could
  disagree on the threshold. Every masternode on mainnet and testnet already
  runs 62058 or later, so the count does not change today. The count is also
  now taken under the masternode-list lock, closing a data race.

## ⛏️ Proof-of-Work Readiness Gate

- **Fixed a missing consensus-readiness gate on every PoW block-production
  path** (`getworkex`, `getwork`, `getblocktemplate`, and the `mintblock`
  debug RPC). The PoS staking path already refused to build blocks before
  voted consensus was ready; the PoW paths did not, which **caused an
  actual testnet chain stall**. All PoW entry points now enforce the same
  readiness check as PoS.

## 💬 Encrypted Messenger — Redesigned

The SMSG messenger has been rebuilt from the ground up around a modern
two-pane chat interface, replacing the dated single-pane page and the
2013-era rich-text plugin.

- **Two-pane layout:** conversation list on the left, live thread on the
  right, with chat bubbles (sent right, received left) rendered via
  `QTextDocument` for inline images and basic rich text.
- **New chat composer** replacing the abandoned MRichTextEdit plugin:
  bold / italic / underline / strikethrough / link / colour, Enter-to-send
  (Shift+Enter for a newline), emoji picker.
- **Emoji support:** 261 standard emoji plus 4 XDN custom emoji, addressable
  by shortcode (e.g. `:xdn:`) and rendered inline as images both while
  composing and in the message thread.
- Conversation previews are HTML-stripped and show a muted single-line
  summary with the counterparty and the receiving address.
- **Fixed: sent messages missing from the Sent list on some wallets.** The
  sender's own outbox copy was encrypted to "the first owned address in the
  address book" rather than the address the user actually sent from. That
  entry varies per wallet, was only format-checked and never checked for a
  retrievable key, and if it happened to be a stealth, watch-only, or
  otherwise keyless address the outbox copy was either not written or
  written under a key the wallet could not decrypt. The recipient's copy was
  unaffected — so the message genuinely sent, but never appeared in the
  sender's own Messages tab, and only on some wallets, which made it look
  random. The outbox copy is now encrypted to the user-selected sending
  address, which is guaranteed owned and already proven encryptable. An
  anonymous send with no usable from-address still falls back to the first
  owned, usable address.
- Fixed several redesign-era issues: messages bouncing back to the list
  instead of staying in the open thread on send, emoji aspect-ratio and
  icon rendering, and vertical layout sizing.
- **Fixed: `smsgdisable` could hang.** Turning secure messaging off at
  runtime waited for the messaging threads while holding a lock they needed
  in order to finish. Issued while a message was being sent, `smsgdisable`
  never returned, and the wallet could then not shut down cleanly.
- **Fixed: unsafe message-bucket access with debug logging on.** A debug
  log line read, and could add to, the message-bucket table without its
  lock, while the messaging thread could be removing entries. Because
  messaging debug output is on whenever any `-debug` category is set, this
  was not limited to `-debug=smsg`. The internal "messaging enabled" flag,
  shared by several threads, is now thread-safe as well.

## 🛡️ Wallet & Maintenance Hardening

- **Very large sends no longer fail as "Transaction amount too small".** The
  check that stops a wallet creating uneconomically tiny payments used
  arithmetic that overflowed above roughly 92.2 million XDN, wrapped to a
  negative number, and declared the payment too small — so the largest
  transactions a wallet could be asked to make were the ones it refused. The
  calculation has been rearranged to avoid the overflow; it gives an identical
  answer for every amount that worked before. This affected the wallet only, and
  could never have produced an invalid transaction.

- **RPC no longer listens on public interfaces by default.** Setting
  `rpcallowip` to *anything* — including `127.0.0.1` — used to make the RPC
  server listen on every network interface. The wallet's own default
  configuration, and the masternode setup dialog, both wrote exactly that line,
  so nodes configured the standard way had RPC reachable from the internet. The
  allow-list and password still protected it, but there was no reason to expose
  it. RPC now listens on loopback unless `rpcallowip` grants a remote address,
  and the line is no longer written by default (loopback was always allowed
  without it).
- **`listtransactions` coinstake amounts corrected.** The amount reported for a
  proof-of-stake coinstake was computed from *every* output in the transaction,
  including payments to other people. Two consequences, now both fixed:
  a masternode payment arriving inside someone else's coinstake reported
  **0.00** — roughly a third of all masternode income, since PoS blocks carry
  the masternode payment in the coinstake — and a staker's own entry was
  inflated by the masternode and devops payments in the same block. Each
  coinstake entry now reports this wallet's own net: its outputs minus its
  inputs. **The wallet's spendable balance was not affected** — `getbalance`
  with no arguments, and the balance shown in the wallet, are computed per
  output rather than through this code. This was a reporting error, but one that
  under-states income to anything building reward accounting on
  `listtransactions`.
- **Recovery routing.** The auto-verify-and-recover path on wallet load no
  longer bypasses the `-salvagewallet` deprecation gate; recovery is routed
  through the safe rebuild path (`RebuildWallet`) rather than the deprecated
  BDB salvage.
- **Berkeley DB error reporting.** Database error paths now name the file
  and translate the error code instead of surfacing an empty filename.

## 📡 Peer Reliability

- **The wallet now recognises when it is still catching up.** It relied on a list
  of built-in checkpoints to decide, which on the test network is empty and on the
  main network stops well short of the current chain — so it believed it was
  up to date far too early. It now compares itself against its peers,
  preferring the peers it connected to itself, so a group of incoming
  connections reporting an inflated height cannot make it think it is behind
  and stop processing masternode messages.
- **The wallet asks for the masternode list again once it has caught up.** It only
  ever asked when first connecting, so a wallet that connected before it was
  synced never asked again and filled its list one entry at a time.
- **A masternode restarting on a shared address recovers on its own.** Where
  several masternodes share one internet address, only the first to restart could
  fetch the list; the others waited for the owner to re-announce them by hand.
  A restarting masternode can now ask for just its own entry, which is answered
  far more readily. This helps with short restarts — a reboot or an upgrade — and
  does not replace re-announcing after a long outage.
  Masternodes that hold their own collateral never needed this and no longer ask
  for it — including while their wallet is locked or their collateral is still
  too new — previously they asked every five minutes indefinitely, because the
  check that was meant to stop them could never be satisfied.

- **IPv6 masternode address changes now propagate.** When a masternode's
  address changed, each receiving node tested it by opening a connection to the
  new address — and marked it disabled if that failed. That measured the
  *receiver's* connectivity, not the masternode's: a node without IPv6 could
  never connect to an IPv6 address, so it disabled every IPv6 masternode that
  moved, stopped passing the change on, and stopped paying it. In a 20-node host
  migration every IPv4 address change took effect immediately and every IPv6 one
  stalled. The test is removed; a masternode is enabled when it is alive, which
  its signed pings already establish. The test was also a blocking network
  connection made inside message handling, once per update received — removing
  it closes a way to stall a node with unreachable announcements.
- **A masternode that changes address recovers without a restart.** A remote
  masternode learned its own address from the first announcement it received
  and never updated it. After a host move it kept signing its pings with the old
  address, which every node holding the new address rejected, so the entry
  expired network-wide even though its address was correct everywhere. It now
  adopts the announced address when an update for itself arrives.
- **`masternode list` status now matches reality.** The RPC could report
  `ENABLED` for a masternode that relay, `dseg` and payment were all skipping —
  which is what made the IPv6 problem above so hard to see. RPC status and the
  Masternodes tab now always agree.
- **`-maxconnections` is now honoured.** It was read at program start-up before
  any options had been parsed, so it was silently ignored and every node ran at
  125 regardless of the command line or the configuration file. It is now
  applied, and clamped to what the operating system's socket polling can
  safely address — honouring it without that limit would have let a high value
  corrupt memory rather than fail cleanly. A reduced value is logged and shown
  as a start-up warning.
- **`-addnode` peers no longer consume the outbound budget.** Added nodes used
  to draw from the same 12 outbound slots as automatically-discovered peers, so
  a long `-addnode` list — for example sibling daemons on one host — filled
  every slot and the node never connected to anything else. Added nodes now
  have their own budget of 8, **in addition to** the 12 discovered peers,
  matching the change Bitcoin Core made for the same reason.
- **`dseep` relay de-duplication.** Repeated `dseep` announcements are now
  de-duplicated before relay, eliminating a bandwidth- and log-flood
  amplification path observed under sustained fleet operation.
- **A freshly started wallet no longer bans its peers over clock
  differences.** A block whose timestamp looked more than 45 seconds in the
  future — judged against the wallet's own clock, which is still settling just
  after start-up — was treated as an attack, and the peer that sent it was
  banned. In one incident a node restarted on mainnet banned 86% of its peers
  and cut itself off. Such blocks are now declined without penalising the
  peer, the tolerance is three minutes, and the check waits until the wallet
  has heard from enough peers to trust its own clock.
- **Stakers no longer produce blocks that are rejected for arriving too
  soon.** A proof-of-stake timestamp is rounded down to a 16-second step, so a
  staker that waited exactly the 45-second minimum block spacing could still
  stamp its block inside it, and the network rejected the block. The staker
  now waits for the first rounded timestamp that clears the minimum. No
  staking opportunity is lost: the earlier timestamps could never have been
  used.
- **Masternode list recovery on a stalled chain.** `dsee` / `dseep`
  processing was gated behind a synchronisation check that reports false
  whenever the chain tip is more than an hour old. A node on a stalled
  chain therefore refused the very messages that would repopulate its
  masternode list, and could never recover a quorum on its own — a stall
  made its own recovery impossible. List population is now governed by a
  dedicated check with no stale-tip test. Field-validated: a node with a
  27-hour-old tip repopulated from 0 to 8 masternodes and met the
  consensus floor.

## 🔧 New Diagnostics

- **`masternode winners` now shows the winners.** Once voted consensus was
  active, any height that had successfully resolved printed nothing at all,
  while heights that had not resolved printed a row — so the blanks were the
  successes and the output read as though consensus were failing everywhere. The
  fault was invisible before activation, when every height legitimately printed
  `pre-activation`.
- **Querying the winners no longer writes false alarms to the log.** Each call
  recorded a "no consensus, falling back to legacy" line for every height it
  looked at — up to thirty per call — in a log operators read to find real
  consensus failures. Block production was never affected; only the reporting
  was. Those lines now appear for block production alone.

- **`getdeploymentstatus` RPC** *(new)* — read-only deployment and
  activation-readiness telemetry, with no new consensus state. Reports the
  build's protocol version and whether an activation height is scheduled on
  this network (`build.consensus_capable`, false on mainnet in v2.0.0.9;
  `activation.scheduled`); the effective activation height, spork-15 state,
  and blocks remaining (-1 when not scheduled); the share of connected peers
  that can take part in queue voting (protocol 62058 or later, so v2.0.0.8
  peers count — a different meaning from `build.consensus_capable`); and —
  the safety signal — the number of voting-eligible masternodes for the next
  block versus the consensus floor. Intended to answer the "is the network
  ready to activate?" question from a single call.
- **`mnver` masternode version attestation** *(new P2P message)*. Until now the
  protocol version shown for a masternode was whatever the *controller wallet*
  stamped when `masternode start` was last run — so a daemon upgraded without
  re-running start kept advertising its old version indefinitely, and the
  network had no way to tell. Each masternode daemon now signs its own
  `PROTOCOL_VERSION` with `masternodeprivkey` and broadcasts it on the existing
  ping cadence. The attested value corrects itself across the network within
  about a minute of an upgrade, with no operator action.

  Older nodes ignore the unknown message, so there is no activation and no
  compatibility break. **The attested version is telemetry only — nothing in
  consensus reads it.** `getdeploymentstatus` reports it under `version_drift`,
  including how many masternodes are attesting, whether any disagree with their
  advertised value, and whether a disagreement crosses the 62058 vote-queue
  floor.
  The Masternodes tab prefers the attested version where one is available and
  marks it, falling back to the observed handshake version and then to the
  advertised value.
- **Queue-capable peer count corrected.** `getdeploymentstatus` was
  comparing connected peers against `PROTOCOL_VERSION` (62059) rather than
  `MIN_VOTING_PROTOCOL_VERSION` (62058), so v2.0.0.8 peers — which *can*
  take part in queue voting — were excluded (reported as
  `peers.consensus_capable`). On mainnet this under-reported readiness
  as 2 of 13 when the correct figure was 9 of 13. The strict
  same-build-version count is still available as `at_current_build`.
- The `checkblock` debug category now surfaces both consensus outcomes per
  validated block (voted-payee match, and consensus fallback with height),
  so operators can measure the post-activation fallback rate directly from
  the log with `-debug=checkblock`.

## 🖥️ Version & Housekeeping

- **Release candidates now identify themselves.** Every v2.0.0.9 build reported
  an identical version string, so `getinfo` could not tell one candidate from
  another and test results could be attributed to the wrong build. Candidate
  builds now carry their candidate number in the version string and declare
  themselves pre-release, which also restores the "pre-release test build"
  warning in the status bar. The released build reports exactly as before.

- Client version reports **2.0.0.9**; internal version strings standardised
  to the four-part `2.0.0.9` form across the source.
- The rescue predicate was renamed `IsRescueActive()` → `ShouldMintRescueBlock()`
  so the name states what it is: a producer-side decision, not a validity
  test. Guardrail comments at both former validator call sites record that
  it must never be reintroduced into `CheckBlock()`. Because the rescue no
  longer sits in consensus, the parallel Rust implementation **does not need
  to mirror the predicate at all** — a producer-side heuristic requires no
  cross-implementation agreement.
- Version regression tests rewritten to the current constants, including a
  guard that fails if the vote-queue capability floor
  (`MIN_VOTING_PROTOCOL_VERSION`) is ever raised in lockstep with the protocol
  version.
- **One version number.** The build now reads the version from
  `src/clientversion.h`; `DigitalNote_config.pri` no longer keeps its own copy,
  which had been left at 2.0.0.8.

## 🎨 Interface

- **The staking indicator no longer reports a fault that is not there.** It
  showed "Staking thread not responding — restart wallet" and then went on to
  stake normally moments later. The wallet pauses between staking attempts to
  respect the minimum spacing between blocks, and the warning was set to trigger
  after exactly the length of that pause — so any wallet that waited out a full
  pause reported a problem it did not have. The warning now allows three times
  the longest pause, and still catches a genuinely stalled thread.

- **"Copy transaction ID" now copies a usable transaction ID.** It appended a
  `-000` suffix, so the copied value was 68 characters and was rejected by
  every block explorer, by `gettransaction` and by the explorer tab. The
  suffix was never an input or output number — it was the wallet's own
  display-row ordinal, which is why it read `-000` on virtually every row.
  v2.0.0.8 removed it from the Transaction details dialog; it survived in the
  right-click copy and in the "ID" column of the CSV export, and both are now
  the bare 64-character hash. A transaction that shows as more than one row
  (a send that also pays you change, for example) now repeats the same ID on
  each of its rows in the export, which is correct — those rows are one
  transaction.

- **Toolbar shortcuts renumbered to match the toolbar.** Masternodes had no
  shortcut and now has **Alt+6**; Block Explorer moves from **Alt+6 to Alt+8**.
  The full set now runs 1-8 in the order the buttons appear: Dashboard,
  Receive, Send, Transactions, Addresses, Masternodes, Messages, Block
  Explorer. **This changes an existing binding** — see Upgrade Notes.
- **Seed-phrase dialog rewritten.** The previous wording described the phrase
  as "a backup of your wallet password", which is wrong and dangerously so: it
  is derived from the wallet's master key, not the passphrase, and it cannot
  restore funds on another machine. **Settings → Recovery Phrase** now leads,
  before the phrase is revealed, with what the phrase is *not*, in line with
  the recovery-phrase upgrade dialog.
- **Log noise removed.** A wallet-status line was being written about four
  times a second — roughly 14,400 lines an hour — and now logs only when the
  status actually changes. Coin-control timing lines are gated behind
  `-debug=selectcoins`.

## 🖼️ Qt6 Migration

The desktop wallet now builds against **Qt 6.8.3** on all six targets. Qt 5.15
reached end of standard support in May 2023; this is the last major toolchain
move before the v3 line.

- **Wallet sources migrated.** The GUI sources were updated for the Qt6 API:
  the removal of `QRegExp`, `QDesktopWidget`, `setTime_t`, `QLayout::margin()`,
  the `QString`/`QChar` implicit-conversion tightening, and the signal changes
  around `QComboBox::activated` and `QCheckBox::stateChanged`. Version-guarded
  where both toolchains must build.
- **Static Qt6 built from source on every platform** — Windows (MinGW64),
  Linux x64, Linux x64 compat, Linux aarch64, and both macOS architectures.
  Only `qtbase` and `qttools` are built: `qt-everywhere` for 6.x unpacks dozens
  of modules the wallet never uses, while `qttools` is required for `lrelease`,
  which generates the `.qm` translation files.
- **aarch64 now cross-compiles in two stages.** Qt5 cross-built in a single
  pass; Qt6 cannot, because the target build has to *run* host tools
  (`moc`, `rcc`, `uic`) that cannot execute on aarch64. A host x86_64 Qt6 is
  built first into a separate prefix and named via `QT_HOST_PATH`.
- **Windows no longer downloads a prebuilt Qt.** The static Qt is built in-job
  and cached, so the toolchain version tracks the build scripts rather than
  whatever was last uploaded as a release asset.

**Visible changes.** The widget style is pinned explicitly on Windows: Qt6
would otherwise select the `windows11` style, which renders menus and table
grids differently from every previous release. The wallet takes the platform
default font rather than loading a bundled one — under Qt5 that load silently
failed on every run and fell back to the platform default anyway, so the
appearance is unchanged and the dead code path is gone.

## 📦 Dependency Uplift

The final dependency modernisation before the planned v3 line.

- **OpenSSL upgraded 1.1.1w → 3.5.7.** OpenSSL 1.1.1 has been end-of-life
  since September 2023; the wallet now builds against the current 3.5.x LTS
  branch. The raw EC / BN / ECDSA / RIPEMD calls used by SMSG, stealth
  addressing, and the bignum layer are marked deprecated in OpenSSL 3.x but
  remain fully available; deprecation diagnostics are suppressed so they do
  not break `-Werror` builds. Migrating those call sites to the modern
  EVP / OSSL_PARAM 3.x API is tracked as future work.
- **Boost upgraded to 1.91.0.**
- **Web-wallet connector migrated from websocketpp to Boost.Beast.** The
  vendored websocketpp 0.8.2 library depended on `boost::asio::io_service`,
  which was removed in Boost 1.87 — so the Boost uplift required replacing
  it. The connector was rewritten on Boost.Beast with its wire behaviour
  preserved 1:1: the same JSON frames, the same text-opcode framing, and
  the same broadcast semantics, so connected web-wallet clients see no
  difference.
- **Boost.Asio API migrations.** Beyond the connector rewrite, the uplift
  removed several APIs the RPC and SSL layers relied on:
  `boost::asio::deadline_timer` (dropped from `boost/asio.hpp` in 1.89),
  `address_v6::is_v4_compatible()` / `to_v4()`, and the old
  `resolver::query` / `resolver::iterator` forms. All call sites were
  migrated to the supported equivalents with behaviour unchanged.

## ⚙️ Build & Release

- **macOS deployment target pinned consistently.** All prerequisite
  libraries and the wallet link now target macOS 12 (Monterey) explicitly,
  independent of the CI runner's SDK. Previously the prerequisite libraries
  inherited the runner's default SDK, which broke the link when GitHub's
  runner image advanced.
- CI continues to build the full six-target matrix: Windows x64, Linux x64,
  Linux x64 (compat), Linux aarch64, macOS Intel, and macOS Apple Silicon —
  now all building Qt6 from source.
- **Windows CI split into separate library and build jobs**, matching every
  other platform. Previously one job did the toolchain, the libraries and the
  wallet, so a failure could not be attributed to any of them.
- **Build scripts now auto-detect the job count.** `compile_libs.sh` forwarded
  its argument with no default, so invoking it without one built every library
  single-threaded. An explicit `-j N` still takes precedence.

## 📅 Coming up: devops address rotation at block 1,280,000

**This release does not change the devops address.** This notice is advance warning
of a scheduled change that has been in the code since v2.0.0.8, so operators have time
to prepare.

> **Correction:** the v2.0.0.8 release notes gave the rotation height as 1,400,000
> (estimated September 2027). That was wrong. The v2.0.0.8 software itself has always
> used **1,280,000**, and so does this release.

### What happens

At **mainnet block 1,280,000**, the address receiving the devops portion of each block
reward changes:

| | Address |
| --- | --- |
| Blocks up to and including **1,279,999** | `dafC1LknpDu7eALTf5DPcnPq2dwq7f9YPE` |
| Blocks from **1,280,000** onward | `dGoFPie9QZmQ1Ty1beqSHytxNruehpGtGa` |

The boundary is **inclusive** — block 1,280,000 itself pays the new address. There is no
transition window and no grace period.

At that same height, validation of the devops payee changes from log-only to **strict**:
from block 1,280,000 onward, a block paying the old address is **rejected by the network**.

### Who needs to do something

**Anyone still running v2.0.0.7 or earlier who stakes or mines must upgrade before
block 1,280,000.** Those versions do not know the new address: they keep paying the old
one, and from block 1,280,000 the network rejects their blocks. Wallets that only send
and receive are not affected by the address change itself, but should upgrade too.

**On v2.0.0.8 or later, almost nobody needs to act.** If your software obtains block
templates via `getblocktemplate`, the correct address is supplied per template and
resolved from the target height — this is handled automatically and no action is
required. Standard wallets, stakers, and masternode operators running v2.0.0.8 or later
need do nothing.

**The exception that matters:** any mining pool, staking service, or custom block-building
software with the devops address **hardcoded**. From block 1,280,000 those blocks will be
rejected and the work lost. If you maintain such software, check now:

```
grep -r "dafC1LknpDu7eALTf5DPcnPq2dwq7f9YPE" .
```

Any hit outside historical data or documentation needs updating, or switching to
`getblocktemplate`.

**Masternode payments are unaffected.** Only the devops payee changes.

### This is not a fork

No consensus rules change at the rotation. It is a scheduled change to a payment
destination that every v2.0.0.8-and-later node already computes from the block height.
There is no coordinated upgrade, no activation ceremony, and no mandatory update beyond
being on v2.0.0.8 or later.

The mechanism was exercised on testnet during the v2.0.0.8 cycle, and again on the
current testnet, where block 99 paid the old testnet devops address and block 100 the new
one. The code path that resolves and enforces the address is unchanged since v2.0.0.8.

In short: if you use `getblocktemplate`, confirm and carry on; if you have a hardcoded
address, update it before the chain reaches 1,280,000.

### Estimating the date

The trigger is a **block height, not a date**. At block 1,254,427 (15 November 2026) the
boundary was about 25,600 blocks away: around 20 December 2026 at the 120-second target
spacing, or around 10 January 2027 at the ~190 seconds per block averaged over the previous
six weeks. Any specific date in circulation is an estimate and will drift — track the height.

## 🔒 Release Candidate 9 — pre-release review fixes

rc9 is the result of two independent pre-release reviews of the whole tree.
Besides withdrawing the mainnet activation height (see *Mainnet Voted-Consensus
Activation*), it fixes:

**Network robustness**
- Malformed secure-messaging (SMSG) traffic could crash or hang a node. Message
  and bucket-list sizes are now checked before use, and processing of a
  malformed batch stops at the first bad message.
- A lock-ordering fault between the SMSG worker and the message thread could
  hang all networking. Both now take the locks in the same order.
- An InstantX code path could crash a node. The dead "reprocess the last 15
  blocks" code behind it is removed.
- The staker took two locks in the opposite order to block processing, so the
  two could deadlock. The staker now takes them in the standard order.
- The per-peer list of requested items is now capped.
- Secure messaging now reads public keys only from blocks the node actually
  accepted.
- A vote queue from an unknown masternode is no longer relayed to every peer;
  the node asks for that masternode's entry instead.

**Masternode payments**
- **Last-paid tracking now credits only the masternode payment output.**
  Previously any coinstake output paying a masternode's address counted as a
  payment, so a masternode whose operator staked from the collateral address
  looked "recently paid" and was pushed back in the payment order. This feeds
  the payee choice on mainnet today. Every masternode sharing an address is
  now credited, and a chain reorganisation recomputes from the correct block.
- `masternode.conf`: blank lines, `#` comment lines and Windows line endings
  are accepted. At wallet start-up a malformed line is skipped with a warning;
  previously it silently dropped that line and every line after it.
  (Starting a masternode still refuses a malformed line.)
- `-mnconflock` is now on by default, as its help always said: collateral
  outputs listed in `masternode.conf` are locked at start-up so they cannot
  be spent by accident.
- `masternode stop` by transaction hash signed the stop message with the wrong
  key, so peers ignored it. Fixed (also in the older stop variant).
- The Masternodes tab's Edit and Add now use the file named by `-mnconf`.

**Wallet**
- **`getrecoveryphrase` now returns the wallet's real recovery phrase**, the
  same one the GUI shows. Before rc9 it returned a different phrase that does
  not restore the wallet. **If you saved a phrase from `getrecoveryphrase` on
  an earlier build, replace it** with the one from the GUI or from the rc9 RPC.
- Rotating the recovery phrase now also saves the re-encrypted stealth-address
  keys. Before rc9, a wallet with its own stealth addresses lost the ability to
  spend stealth funds after a rotation plus a lock or restart. The rotation now
  also holds the wallet lock throughout, so a key created while it runs (for
  example a key-pool top-up by the staker) can no longer be lost.
- After a rotation the wallet now insists that you confirm you have written
  down the new phrase ("I have written down my new 24-word recovery phrase")
  before the dialog can close. The old phrase stops working the moment the
  rotation completes.
- Removing a watch-only address could leave the wallet in a state that crashed
  `listtransactions` or the next incoming transaction. Fixed.
- If a Compact Wallet run was interrupted between its two file renames, the
  next start created an empty wallet and hid the real one (still safe in
  `wallet.dat.bak` / `wallet.dat.new`). Start-up now completes the swap, or
  stops with instructions if it cannot.
- The `spork` RPC truncated large values: the documented "off" value
  4070908800 became a negative number, which switched a time spork **on**.
  Fixed; the help now describes each spork type.
- `help mintblock` no longer mints a block.
- `dumprawwallet` honours `-wallet=`. Its help now warns that the dump file
  contains private keys for an unencrypted wallet and stealth scan secrets.
- `-disablewallet`: guarded the idle mixing timer and the two blockchain-scan
  RPCs, which assumed a wallet.
- The GUI "unlock for staking only" option is now passed to the right
  parameter (the end result was already correct).
- `getvoteinfo` with no argument now reports the next block (tip + 1), the
  height producers and validators use. It used to report tip + 10, which never
  showed consensus.

**GUI**
- The recovery-phrase dialog no longer touches widgets from a worker thread,
  clears the clipboard on close if it still holds the phrase, and no longer
  risks closing the app when a typed phrase does not match (Verify).
- The Messages view no longer writes contact labels and addresses to
  `debug.log`.
- The debug console ignores blank commands.
- Corrected texts: Check Wallet showed a literal "%3"; Compact Wallet promised
  an automatic restart that does not happen; the "Decrypt Wallet" label pointed
  to a feature the GUI cannot reach; example masternode port 51441 is now 18092.

**Help text and documentation**
- `-help`: correct default ports (P2P 18092 / testnet 28092, RPC 18094 /
  testnet 28094), `-mininput`, `-checklevel`, `-blockmaxsize`,
  `-masternodeminprotocol`, `-instantxdepth`; `-masternodepaymentskey` is now
  listed; `-scaleblocksizeoptions` (never read) is removed; `-liveforktoggle`
  is marked as having no effect. **`-webwallet` now says what it does: it
  starts an unauthenticated WebSocket server on all IPv4 interfaces (port
  7778) that pushes secure-message contents to any client.** Leave it off
  unless you know you need it.
- RPC help examples use this network's RPC port instead of 9998.
- **`smsgscanbuckets` and `smsgbuckets dump` delete the SMSG bucket files.**
  Their help now says so. Do not run them expecting a harmless rescan.
- `walletpassphrase`'s third parameter is documented as `stakingonly`;
  `settxfee`, `lockunspent`, `listlockunspent`, `checkwallet`, `repairwallet`,
  `masternode current` / `enforce`, `getmnlastpaid`, `getvoteinfo`,
  `listequivocators` and `clearequivocator` help corrected.
- Many source comments corrected, notably: there is no 45-minute
  payment-check warm-up after start-up (a restarted node checks payees as soon
  as it leaves initial block download); the devops rescue is producer policy,
  not a validity rule; equivocation marking was removed in v2.0.0.8.
- Removed the obsolete `src/masternode_upgrade_notes.md` (its v2.0.0.7 advice
  would now split the chain) and the uncompiled `guiutil_hidpi_additions.cpp`.

## 🧾 Release Candidate 10 — balances that match what you can spend

rc10 changes only what the wallet shows and says. Nothing on the network or in
consensus changes.

**Change shows as Pending until its first block**
- The wallet has never spent change before it has one confirmation, but it
  counted unconfirmed change as **Available**. A second send in the same block
  could pass the balance check and then fail with "Insufficient funds".
- Unconfirmed change now shows as **Pending** for about one block (2 minutes on
  average). For example, sending 1,000 XDN from a single 2,500 XDN coin:
  Available drops by 2,500 and about 1,500 shows as Pending until the next
  block. Total drops by 1,000 plus the fee, as before.
- A second send inside that block is now refused straight away ("The amount
  exceeds your balance." in the GUI, "Insufficient funds" over RPC), instead of
  failing later.
- `getbalance` now reports what can be spent right now. To get the old
  display, set `confchange=0` in `DigitalNote.conf`.
- In the transaction list, your own unconfirmed sends show grey until their
  first block.

**InstantX**
- A locked InstantX payment counts as **Pending**, not Available, until its
  first block, because it can't be spent before then either. This applies to
  payments you send and payments you receive.
- In the transaction list, a locked transaction that is not in a block yet now
  reads **"Locked (InstantX)"** with a lock icon, instead of "Confirmed (10
  confirmations)". This text is in English only for now.
- RPC help: for `gettransaction`, `listtransactions`, `listsinceblock`,
  `listreceivedbyaddress`, `listreceivedbyaccount` and `getbalance`, the help
  now says that `confirmations` includes the InstantX depth. It reads 10 higher
  (`-instantxdepth`) while a transaction is locked. `bcconfirmations` counts
  blocks only. Services that need the real block count should read
  `bcconfirmations`, or run with `instantxdepth=0`.
- With `-reservebalance` set, the staker now counts only coins that can be
  spent now.

## ⚠️ Upgrade Notes

- **Chain-compatible with v2.0.0.8.** Network protocol bumped to 62059; older
  clients still connect and sync (see the timestamp qualifier at the top).
- Every masternode whose collateral is deep enough counts toward voted
  consensus, whatever version its controller advertises — no masternode is
  dropped from consensus eligibility by upgrading.
- **Voted consensus is not scheduled on mainnet in this release**, and
  mainnet ignores `SPORK_15`. Mainnet payment selection stays on the
  pre-activation path (each producer picks from its own masternode list).
  A later release will schedule activation and say what to upgrade first.
- No mandatory upgrade for this release — but the devops address rotation at
  block **1,280,000** requires v2.0.0.8 or later for anyone who stakes or
  mines (see *Coming up*).
- The rescue items below apply only where voted consensus is active, which in
  v2.0.0.9 means **testnet**.
- **Rescue blocks become rarer.** Two changes reduce them: the stall is measured
  honestly, and a wallet with an incomplete masternode list no longer mints them.
  On the test network these accounted for roughly 3% of all blocks over a day,
  every one of them a masternode payment that went to the development fund
  instead.
- **Masternodes on a shared address no longer need re-announcing after a quick
  restart** — only after a long one, where the network has already dropped them.
- **A new peer-to-peer message is used** to request a single masternode entry.
  Older nodes ignore it and are unaffected.
- **Masternode operators should expect fewer rescue blocks and no change to
  anything they do.** Recovery after an outage is unchanged: restart the daemon,
  and re-announce from the collateral wallet only if it was down long enough for
  the network to drop it.
- **Rescue blocks should become rarer again.** The network can now recover from
  a full restart on its own, so the rescue is left to do the job it was built
  for: carrying the chain through a genuine shortage of available masternodes.
- **RPC binding changed.** If your `rpcallowip` entries are all loopback (for
  example `rpcallowip=127.0.0.1`), RPC now listens on loopback only — local tools
  are unaffected. If any entry grants a remote address, RPC listens on all
  interfaces exactly as before. **If you reach RPC remotely, make sure the remote
  host is listed**; a loopback-only list never allowed remote access anyway, so
  nothing that worked before stops working. Note that `rpcallowip` entries are
  wildcard patterns (`192.168.1.*`), not CIDR ranges: `0.0.0.0/0` matches nothing,
  while `*` matches everything.
- **IPv6 masternodes will start being paid by upgraded nodes.** Nodes without
  IPv6 previously never paid IPv6 masternodes. This improves as the fleet
  upgrades; nodes still on older releases keep the old behaviour, and every block
  remains valid to every node in the meantime.
- **A masternode is no longer required to accept inbound connections from each
  peer to be paid.** It must still be running and pinging. The old
  connection test was the only check of this kind, it could be bypassed by
  re-registering, and it wrongly excluded honest IPv6 masternodes.
- **`-maxconnections` now takes effect.** If you have it set, it will now be
  applied — previously it was ignored and 125 was always used. Check any value
  you set long ago still makes sense. Configuration files that the wallet
  generated itself contain `maxconnections=150`, so those nodes will now accept
  up to 150 connections instead of 125.
- **`-addnode` behaviour changed.** Added nodes are now additive rather than
  competing with discovered peers, so a node with an `-addnode` list will open
  more connections in total than before (up to 12 discovered + 8 added). If you
  relied on `-addnode` to *limit* peers, use `-connect` instead. An `-addnode`
  entry without a port still resolves to the default port (18092): siblings on
  other ports must be written `IP:port`.
- **`masternode winners` output changed.** A height with no winner used to show
  an empty string, which looked like a fault. It now shows `"pre-activation"`
  (voted consensus not active — the normal state on mainnet, where activation
  is not scheduled in this release) or `"unresolved"`. **Anything treating any non-empty value as an
  address must be updated.**
- **`testnet=` in a configuration file does not select the network.** Only the
  `-testnet` command-line switch does. A node configured the conf-file way
  starts on **mainnet**, silently. A relative `-conf` path is resolved inside
  the network's data directory (`testnet/` under `-testnet`); an absolute path
  is used as-is.
- **One keyboard shortcut changed.** Block Explorer moves from **Alt+6** to
  **Alt+8**; **Alt+6** now opens Masternodes. Anyone with muscle memory for
  Alt+6 will land on a different tab.
- **Unconfirmed change no longer counts as available** (from rc10). For about
  one block after a send, `getbalance` and the GUI's Available leave the
  change out; it shows as Pending. A service that sends several payments in a
  row from one wallet will have the next one refused until that block arrives,
  unless the wallet holds other confirmed coins. Those sends already failed
  before rc10, only later. `confchange=0` restores the old balance figure; it
  does not let the wallet spend unconfirmed change.

**Recommended upgrade order for masternode operators:**
1. Masternodes
2. Mining pools
3. Stakers
4. Full nodes

## 🔍 MISC

- No new consensus constants were introduced by the rescue mechanism; its
  timing constants are producer policy, and validators do not evaluate them.
  Whether a producer mints a rescue block depends on its own view (clock,
  peers, vote queues, masternode list), so producers may differ on when.
- The devops rescue payee is taken from the existing height-indexed devops
  address ladder, so a rescue block is easy to identify, and every node
  accepts it.
